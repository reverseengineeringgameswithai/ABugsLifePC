Capture boundary and fail-closed rule
-------------------------------------
The intended hardware execution breakpoint at 0x0044C898 was rejected after
RUN-GDB-20260813-101022 stopped there once and then received structured
same-PC SIGSEGV. Its points were deleted, it detached, and all five survival
samples passed under nopass. Accepted arms therefore use no execution
breakpoint.

One hardware access watch at 0x005B18E0 stops after the exact post-call load
at 0x0044C8A5, reporting PC 0x0044C8AB and the still-current RSI entry
pointer. Between return 0x0044C89E and this stop, native code only restores
EDI, pops the argument, and loads 0x005B18E0; it does not touch counter
0x008082C8, capacity 0x0081C138, or base pointer 0x0081BC28. Nonmatching
accesses remain in stops.jsonl but do not enter the ordered capture.

The zero_post mode accepts only the coherent all-zero triple
(counter, capacity, base) = (0, 0, 0). Native 0x0044F8E0 only increments this
counter after counter < capacity and contains no counter reset/decrement.
Thus an accepted zero post proves exact pre=post=0 and an empty record
interval for that call. Any active or inconsistent arena fails the arm.

Result
------
Bounded negative. The exact M2.24 candidate streams are reached by the caller,
but none emits into this 0x80-stride arena in any tested Direct3D arm because
the arena remains inactive. This contradicts treating the conditional static
arena path as the active explanation for M2.20's visible result. It does not
rule out other effects of 0x0044F8E0, another retained-entry consumer, a
different renderer path, or later copied state.
