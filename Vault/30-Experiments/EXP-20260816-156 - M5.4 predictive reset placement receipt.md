# EXP-20260816-156 - M5.4 predictive reset placement receipt

## Status

**Pre-registration.** Everything below the horizontal rule was written and
committed **before** any game launch, so the prediction cannot be fitted to the
observation. The observed section is appended afterwards in a separate commit.

## Question

M5 exit gate 4 asks whether an independent module is demonstrably safer and
more useful than the original path. For this module the authoring task is:
"if I move a type-1 row, where will a reset put the player?" The original path
is to edit, launch, die, and look. This packet asks whether
`scripts/type1-reset.py` answers it exactly, offline, in advance.

## The edit

Novel in the field that has never been runtime-tested: EXP-20260815-116/117
moved row 6's **X**; this moves row 6's **Z**. Row 7 was left alone because
testing it would require proving a new walkable trigger point, which
[[PC Flik teleport procedure]] forbids without prior evidence; row 6's Z is
equally untested and reuses the already-accepted trigger and walkable point.

Source `CD/LEVEL03/LEVEL.DAT` SHA-256
`bda28dc7287ebc3648998425b3c09f19d6470a85c9fcd439cca5ad8e391c0f2b`; row 6 at
file offset `0x4A4` is `(15678, 0, 15438)`. The candidate sets Z to `15694`
(`+256`), changing exactly one byte at file offset `0x4AD`, and has SHA-256
`91a27776b84626ba400817cb5968699f685a3b9fbbeb63bff101e5d514cb8965`.

Reproduce with the existing guarded editor, which verifies the source hash,
the table identity, the old position, size, reparse, and an exact inverse:

```python
from ablpc.level03_type1_row_mod import _edit_exact_type1_row
_edit_exact_type1_row(
    source_bytes,
    expected_source_sha256="bda28dc7287ebc3648998425b3c09f19d6470a85c9fcd439cca5ad8e391c0f2b",
    expected_table_index=1, expected_table_offset=0x458, expected_count=18,
    row_index=6, expected_position=(15678, 0, 15438),
    output_position=(15678, 0, 15694),
)
```

`TERRAIN.ALL` is **not** touched, so the terrain is byte-identical between
arms and the accepted walkable point stays walkable.

## Registered predictions

Query point for both arms is the independently accepted walkable point
`(501696, 30092, 494016)` (EXP-20260815-130, EXP-20260816-141), which the
engine adopts into the auxiliary triple after the teleport.

| Arm | Selected row | Reset X | Reset Y | Reset Z |
| --- | ---: | ---: | ---: | ---: |
| Control (retail DAT) | 6 | 501696 | 30092 | 494016 |
| Candidate (`+256` Z) | 6 | 501696 | **31768** | **502208** |

The candidate's Z is `15694 << 5`. Its Y is **not** a shift of anything: it is
the terrain height recomputed at the moved point, `31768`, which differs from
the control by `+1676`. That margin is more than an order of magnitude larger
than the 121-126 unit settle band, so the two arms cannot be confused.

Also predicted, and equally falsifiable:

- the selected row stays 6 in both arms — the edit moves the placement, not
  the selection;
- the winning terrain descriptor is 552 in both arms;
- the candidate point carries only result-0 planes, so the reset lands on
  ground and must **not** produce a repeating `NextLife=2` loop. (A `+512`
  edit would instead land on descriptor 572 at Y `64032`, the pit — the model
  says so offline, and that edit is deliberately not the one under test.)

## Falsification conditions

The module fails if any of the following is observed:

- reset X or Z differs from the table by any amount;
- reset Y at the write instant differs from the predicted value by more than
  the settle band, or the candidate's Y is not about `1676` deeper than the
  control's;
- a row other than 6 is selected in either arm;
- the candidate arm produces a reset loop, contradicting the result-0
  prediction.

A sampler that misses the write instant and catches an adopted, settled value
is a **measurement limitation, not a pass**: it will be recorded as such, with
the settled value and its offset from the prediction.

## Planned procedure and write boundary

Per arm, on a derived copy under `work/copies/` with the auto-hardware build:

1. launch detached, confirm the six hardware-Direct3D markers from the log;
2. select Tunnels from the carousel; confirm internal level `0x00861C84 == 3`;
3. start the read-only observer (current, preceding, auxiliary, flags
   `0x0059D9A0`, `NextLife` `0x0059A5B0`, level, collision);
4. one 24-byte `process_vm_writev` of current+preceding to the accepted
   walkable point, per [[PC Flik teleport procedure]]; verify `NextLife=0` and
   adoption into auxiliary;
5. trigger the selector with the EXP-20260815-117 accepted setup: byte `0x18`
   at `0x0059D9A0` and word `0x0002` at `0x0059A5B0`;
6. sample the auxiliary triple across the write.

Exactly three target writes per arm, all inside previously accepted
boundaries. No debugger, breakpoint, register, code, executable, asset, or
`originals/` write. Owned process group and private sink closed afterwards
with a clean audit, and Wine `Y:` restored to the retail copy.

This is a **write-assisted** trigger, not natural gameplay, and the receipt
will say so.

## Observed

Both arms ran on the guarded auto-hardware build
(`1e1d5099...c8a9c41f`) from a `work/copies/` cwd, each passing all six
hardware-Direct3D markers with zero `INITSOFTRENDER` and no
`SYSTEM MEMORY ONLY`. Internal level `0x00861C84` read `3` in both. Raw traces
and both arms' logs are retained at
`work/copies/EXP-20260816-156-evidence/`: `control-trace.tsv`,
`candidate-trace.tsv`, `control-bugs.log` (SHA-256 `85b39abf...`),
`candidate-bugs.log`, and two frames. The control log is retained because the
game recreates `bugs.log` in its cwd on every launch, so the live file is
volatile.

### Control arm (retail tree, `Y:` at the retail copy)

Teleport wrote 24 bytes; the engine adopted the point into the auxiliary
triple. The trigger then read back flags `0x0018` and `NextLife=2`, and 21 ms
later flags cleared to `0x0001` with `NextLife=0` and Flik placed at
`(501696, 30215, 494013)`.

The auxiliary triple stayed `(501696, 30092, 494016)` — the predicted control
placement. **This arm cannot distinguish a write from a no-op**, because the
query point and the predicted output are the same point. It is reported as a
baseline for the trigger's behaviour, not as a confirmation of the placement.

### Candidate arm (`+256` Z tree, `Y:` repointed then restored)

| Quantity | Predicted | Observed | Delta |
| --- | ---: | ---: | ---: |
| Reset X | 501696 | **501696** | 0 |
| Reset Y | 31768 | **31768** | 0 |
| Reset Z | 502208 | **502208** | 0 |

At `t = 604.5 ms` the trigger set flags `0x0018` / `NextLife=2`; at
`t = 610.7 ms` — 6.2 ms later — the auxiliary triple became exactly
`(501696, 31768, 502208)` and `NextLife` returned to 0. Every registered
condition holds:

- all three components exact, including the terrain-recomputed Y, which is
  `+1676` from the control and could not have been produced by any shift of
  the edited field;
- the selected row stayed 6 in both arms;
- no reset loop: the retained trace holds exactly one `NextLife=2` row (at
  `t = 604.5 ms`), and `NextLife` then stayed 0 for the remainder of the
  retained window — `610.7 ms` to the final row at `3076.1 ms`, about
  **2.47 s** — confirming the result-0 prediction for the destination. The
  sampler was configured for 8 s but prints only rows where state changes; it
  stopped emitting at `3076.1 ms`, consistent with the game halting once the
  focus loop ended. No retained artifact covers the interval after that, so
  the claim is bounded to the 2.47 s that is actually retained.

Flik then settled to `(501692, 31897, 502240)`, i.e. `+129` deeper than the
written Y. That is **3 units outside** the previously recorded 121-126 settle
band; the control arm in the same session settled at `+123`, inside it.

The band is therefore restated as the **observed extremes over the cited
receipts, 121-129** — EXP-20260815-129's `+123`, the two EXP-20260815-137
standing points at `+121` and `+126`, this packet's control at `+123`, and
this packet's candidate at `+129`. It is a descriptive range of five samples,
not a guarantee or a modelled quantity, and no prediction in this packet
depends on it. `scripts/type1-reset.py` and
[[PC type-1 reset placement resolver]] are updated to the same range so the
tool cannot emit a band that excludes an accepted receipt.

## Result

`ACCEPT` at the module boundary. The resolver predicted, offline and in
advance, the exact triple the original executable wrote — including a Y that
required the composed terrain model. For this authoring task the module
answers in one command what the original path answers only by editing,
launching, and dying, so M5 exit gate 4 is supported **for this module at its
Level03 boundary**. No claim is made for other levels, other type-1
consumers, or any other module.

## Write boundary and lifecycle

Exactly three target writes per arm: one 24-byte `process_vm_writev` of
current+preceding to the independently accepted walkable point, and the
EXP-20260815-117 setup (byte `0x18` at `0x0059D9A0`, word `0x0002` at
`0x0059A5B0`). No debugger, breakpoint, register, code, executable, asset,
save, or `originals/` write. Each helper call revalidated pid, process group,
cwd under `work/copies/`, and the executable SHA-256 before touching memory.

This is a **write-assisted** trigger, not natural gameplay. It reproduces the
already-accepted EXP-20260815-116/117 setup and does not establish controller
reachability.

Both owned process groups (`342058`, `344075`) were terminated, both private
sinks removed, the final process and sink audits are empty, Wine `Y:` is
restored to `work/copies/BUGS_PC-full-disc`, and the retail DAT, retail
executable, and `originals/` hashes are unchanged.

## Methodology finding

Short synthetic key taps are unreliable here. The menus poll
`GetAsyncKeyState`, and an `xdotool key` press lasting about 12 ms is often
missed between polls — two of three carousel presses were dropped that way.
Holding the key across several frames (`keydown`, ~180 ms, `keyup`) landed
every press in both arms. This extends [[PC autonomous game control]], which
specifies XTEST but not a hold duration.
