# Function 0x0041C420

## Summary

Rebuilds the 64-record runtime table rooted at `0x0059B628` from a separate
64-record source table rooted in the `0x00599EB0` type-35 copy.

## Confirmed

- Clears `0x2100` bytes rooted at `0x0059B628` at
  `0x0041C424–0x0041C430`.
- Walks exactly 64 source records at `0x1C` bytes and destination records at
  `0x84` bytes. Evidence: `0x0041C58A–0x0041C597`.
- Skips source records whose observed byte at source `+0x0C` is zero and
  stores a pointer back to the source record at `0x0041C490` for active
  entries.
- Calls `0x0041BD10` at `0x0041C559`; that helper writes the nonzero-gated
  source `+0x0C` byte to destination `+0x00`. For slots 2 and 3, the source
  records are `0x00599EE8` and `0x00599F04`.
- Runs at `0x004679A0` after both `LEVEL.RAW` and `LEVEL*.DAT` processing and
  immediately before the plant batch loader at `0x004679C2`.

## Inferred

This function transforms one `LEVEL.RAW` type-35 table into runtime scene
records. Field meanings and complete record semantics remain unknown.

## Unknown

- Which exact source record/field contributes Level 01's early plant ID 7.
- Meanings of the source type byte, flags, installed callback pointers, and
  downstream runtime fields.
- Whether any transformed entry corresponds to an M1 scene placement. M2.40
  proves that the first-dword and conditional-zero lineages for slots 2 and 3
  do not derive from the established M1 record/payload route.

## Next discriminating experiment

Only if the later M1 placement bridge requires it, bind one selected
`0x0059B628` record back to its exact type-35 source offset and visible
placement with a bounded, approved runtime trace.

## 2026-08-16 addition from EXP-20260816-172

The "type-35 table" is named by the executable itself: the loader copy that
fills the `0x00599EB0` source table logs
`LOAD: Type 35, CreatListRam.` (string `0x004DE2FC`) immediately afterwards, at
`0x0046576F`. Type 35 decimal is the `0x23` record type tested at
`0x00465748`, and the copy at `0x0046574D`-`0x0046576A` moves exactly `0x700`
bytes — `0x700 / 0x1C = 64`, one source record per pool slot.

Further facts from that census:

- The call at `0x004679A0` is **gated**: `test al,0x10 / jne 0x4679CA` at
  `0x0046799C` on a byte of `0x005C5E88`, so not every level builds the pool.
- The per-type setup switch at `0x0041C493` (byte table `0x0041C600`, jump
  table `0x0041C5B0`) has a domain of exactly type 6..41. Within that domain it
  does **not** treat every type alike: 9 types get both a positive count of
  1-8 in source `+0x10` and one of ten thunk pointers at slot `+0x7C`
  (6, 9, 10, 13, 15, 17, 34, 37, 39); 5 get only a thunk (16, 22, 29, 31, 36);
  5 get only a count (12, 18, 19, 40, 41); and 17 take the default arm and get
  neither (7, 8, 11, 14, 20, 21, 23-28, 30, 32, 33, 35, 38). The same 6..41
  domain appears in `0x0041B9F0`.
- The type byte reaches `mov cl,[eax+0x4c881f]` and
  `mov byte [eax*8+0x599ca8],cl` at `0x0041C468`-`0x0041C47D` with only a zero
  test, so `type >= 64` indexes past the `0x200`-byte region cleared at
  `0x0041C432`. Recorded as `KU-069` together with three sibling unbounded
  indexes in the same subsystem: source `+0x0D` into the 40-entry script table
  at `0x0041BD45`, VM opcode 13's operand into the 28-entry sequence table at
  `0x0041E01A`, and VM opcodes 4/10's raw source `+0x0E`/`+0x0F` byte into the
  table `0x005C5860` at `0x0041DDD4`/`0x0041DEE1`, whose load-time clear covers
  64 dwords. No PC level file
  has been parsed for the actual byte distribution.
- For source `+0x12` bit-`0x20` records only, `0x0041C52A`-`0x0041C551` shifts
  source `+0x00`/`+0x04`/`+0x08` left 5 **in place** and writes an incrementing
  per-level counter into source `+0x19`. The initializer then overwrites the
  record's position with the unshifted source values at
  `0x0041BD76`-`0x0041BD84`, so the net effect is one shift, not two.

## Later findings (2026-10-02 audit pointer)

- [[EXP-20260908-005 - Compact terrain storage and actor selector limits]] and
  EXP-20260911-003: the counter written to
  source `+0x19` (`0x0041C54A`) is a compact contact selector, 1..N across
  flag-`0x20` records only, with no bound; `0x0041DA30` reads it for
  movement. The sixteenth aliases camera slot 16, so authoring rejects more
  than 15 such actors.
- The flag-`0x20` branch also snaps Y to the floor plus `0x3200` through
  thunk `0x00401721 -> 0x004ABE00` (`0x0041C55E`-`0x0041C587`).
- **2026-10-12, offset settled statically (raw decoding and decompiled text).**
  - At `0x0041C579` (`add eax, 0x3200`) the floor result is stored to
    record `+0x10`, `+0x34` and `+0x40`, and to the source row's Y
    (`[edx+4]`).
  - Positive Y is downward, so every flag-`0x20` record (the 130 retail seed
    rows) sits `0x3200` runtime units, 400 stored units, **below** the floor
    under it.
  - `scripts/map-original-levels.py` records that plain floor
    (`native_floor_y`). The maps' seed markers are therefore 400 stored units
    above the runtime record.
  - Whether the visible seed is drawn at the record's Y or offset from it is
    unknown. One read-only spawn observation decides it.
- Retail census (2026-10-02 audit, `original_levels.creature_rows` over the
  17 hash-checked engine RAW files): 130 type-11 rows carry `+0x12` = `0x38`
  (bit `0x20`). No row has type >= 64 or script byte `+0x0D` >= 40, so those
  two KU-069 indexes stay in range for shipped data; the VM operand indexes
  were not checked.
