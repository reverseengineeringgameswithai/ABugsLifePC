# Function 0x004A3480

## Summary

Creates the DirectSound object and records a ready flag. Reached through
thunk `0x00401B95`; callers `0x00412CAB`, `0x00412DE5`, `0x0042BAD0`.

## Confirmed

- Clears two `0x300`-dword tables at `0x007EDF08` and `0x007ECE58`, and
  zeroes `0x007ECA44` and `0x007ECA40`.
- Calls `DirectSoundEnumerateA` through thunk `0x004AFEB4` with callback
  `0x004017C1`, itself a `jmp` to the real callback `0x0049DD00`.
- Calls `DirectSoundCreate` through thunk `0x004AFEAE` with the GUID pointer
  from `0x007EDA60`, storing the object at `0x007EDAE8`.
- On a non-null object, calls vtable `+0x18` with the window handle from
  `0x0059F73C` and argument 1, then sets `0x007ECA40` to 1 and calls
  `0x0040123A` with argument 1.
- The `0x007ECA40` write is on the success path only, so it is a usable
  "audio came up" discriminator for a later read-only runtime check.

## Inferred

The vtable `+0x18` call with `(object, hwnd, 1)` has the shape of a
cooperative-level setter, but the interface layout has not been confirmed
against a runtime object.

## Unknown

The roles of the two `0x300`-dword tables, of `0x007ECA44`, and of
`0x0040123A`. Whether enumeration ever selects a non-default device.

## Later findings (2026-10-02 audit pointer)

- [[EXP-20260817-185 - PC event subsystem static census]]: call site
  `0x0042BAD0` lies in `0x0042BA60`, the create callback of the `"DIRECTX"`
  event record `0x004D81E8`, called through the register slot at
  `0x0042DC2A`. That is a static path, not an observed call.
- Call sites `0x00412CAB`/`0x00412DE5` resolve (Ghidra nearest-entry
  inference) to `0x004129A0`, which [[PC FMV playback]] reads statically as
  the FMV player. Why bring-up is reached from there is not established.
- No later note records the read-only sampling of `0x007ECA40`/`0x007EDAE8`.
  EXP-20260910-004 saw
  nonzero DirectSound buffer slots on a derived build; that is
  allocation evidence only. The experiment below is still open.
